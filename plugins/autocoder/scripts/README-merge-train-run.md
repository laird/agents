# Merge train run (assembly, gate, publish, red-batch rules)

`merge-train-run.py run` is one cycle of a merge train; `merge-train.py` (queue and planner) picks the members.

1. Take the **lease** (an flock in the train state dir; one train per repo and integration branch; the OS frees it when the process dies).
2. Run the project's **preflight** hook; a non-zero exit refuses the cycle before any scratch tree is cut.
3. Fetch again (the preflight can take minutes; a tip pushed meanwhile, a rebase after a sibling landed, is the tip to plan). Tell each `regenerate-only` item of the queue ONCE per tip (`regenerate-only.tsv` in the state dir) which files it changes and why no train takes it (train_lib's `regeneratedMergeDrivers`); it is never planned at that tip. Tell each `tip-moved` item once per tip (`tip-moved.tsv`: its tip carries work its READY did not name; not READY until a READY names it), each `foreign-branch` item once per tip (`foreign-branch.tsv`: its READY names a branch that does not belong to the issue, by name or by a `stack:` line; train_lib's `branchOwnership`; never planned) and each item whose rebased or fast-forwarded tip was taken in the named sha's place once per tip (`followed-tip.tsv`; train_lib's `readyTip`). Plan up to the **adaptive limit** of members, **assemble** them as one tree on `train/<UTC>-<n>` (each member's *recorded* tip, regenerated by the project's hook and committed, so the tree the gate records is the tree it publishes), push it. Every planning and assembly merge runs with the repository's hooks off: the project's regeneration (`hooks.regenerate`) runs once, on the assembled tree, never per candidate. Each candidate's probe is a `plan` timing row (seconds, verdict), so the landing report shows planning time beside gate time.
4. **Gate** it through `merge-to-integration.sh` (contract unchanged: exit 0 plus a `merged into` line = landed). A gate that pushed the integration branch landed the set whatever it printed afterwards: git is the proof.
5. **Publish and close out**: every member's work must be in the LANDED commit before its issue is closed with a per-member comment (naming the proof), its branch deleted under a lease on the recorded tip, and an issue closed under a newer READY reopened. The **landing proof** (`train_lib.landing_proof`) is one of `ancestor` (the tip is in the branch's history), `patch` (every commit is patch-equivalent to one there: the gate lands by rebase) `content` (merging the tip into the branch adds nothing, `git merge-tree` with the repository's merge drivers: the gate squashes a branch that holds merge commits, so a train lands as ONE commit no member tip is an ancestor of) or `rows` (the re-merge changes nothing but the order of lines inside files a merge driver owns: a keyed-row driver derives its row order from the merge's ancestor, so a train the gate rebased onto an integration branch that moved under it holds a member's rows in another order than the proof's re-merge writes them; same rows, same work; a reorder in a file no driver owns is the branch's own change and proves nothing). A path merged by one of `regeneratedMergeDrivers` keeps the landed copy in the re-merge (the landing regenerates it from its sources; its generator never runs in the probe). The queue's `on-master` state and the newer-READY reopen read the same proof, so a squash-landed member is never planned again. Then the project's **`landed` hook** runs once per landing (an upstream sync, a drift check), with `AUTOCODER_TRAIN_LANDED`, `AUTOCODER_TRAIN_BASE`, `AUTOCODER_TRAIN_BRANCH`, `AUTOCODER_TRAIN_INTEGRATION`, `AUTOCODER_TRAIN_MEMBERS` (the proven members, `issue<TAB>tip<TAB>branch` rows) and `AUTOCODER_TRAIN_UNLANDED` (the rest) in its environment; it cannot unland anything, a failure is logged and reported. A member that is a dependency-bot tracking issue (train_depbot.py: its body carries `<!-- depbot-pr <n> -->`) also closes its PR with a comment naming the landed sha, before its branch is deleted.

## The daemon (`merge-train-run.py daemon`)

The train launches itself. Each tick reads the queue (one fetch and one tracker listing; no scratch tree) and, when it holds a launchable item (the queue's `queue` state: not `hold`, not `in-lane` behind a live gate, not `in-train`, not `launched` at this tip) and no train holds the lease, runs ONE cycle in the same process; otherwise it sleeps `--interval` seconds (60). A cycle that planned members is followed by the next tick at once (items past the batch limit are still waiting); every other tick sleeps first, so launchable items the planner skips (a conflict, a fault) cost one preflight per interval, never a hot loop. The holds, the lane and launched tips are the queue's own rules; the daemon adds two files in the state dir: `daemon.pause` (its text is the reason; every launch is held while it exists; `daemon --pause REASON` / `--resume`) and `daemon.stop` (`daemon --stop`: the loop ends at its next tick, a running cycle finishes first; a `kill` leaves the cycle record for the next start's reconcile). One daemon per state dir (`daemon.lock`; a second exits 1 naming the holder). `daemon --status`, and `status`, print whether it is live, paused or stopping and its last tick (`daemon.json`). `--once` is one tick (a cron line, a test); `--max-ticks N` bounds a run.

Why: measured on one project, a READY waited 2 to 15 minutes on every cycle for a person to notice it and type `run`, with the gate idle meanwhile. With `train.redMaster` set (README.md "Merge trains": an open tracker issue carrying the configured label whose title starts with the configured prefix is a red integration branch), a tick whose every launchable item is `held` is `idle` with the note `<n> held: red master #N`, logged once per change: only the red's own fix, a lane-labelled branch or a documents-only diff launches a cycle while it is open. The gap is now a ledger row: the cycle writes `launched` per member at the moment it takes it (whoever ran the cycle), and the weekly report shows **READY to launch** (p50, p90, max) from the newest READY before it.

A tracker call that died in transport is retried before it counts (issue #367). `train_lib.tracker` matches the
failure text against `TRACKER_TRANSPORT_ERROR` (a connect that timed out or was refused, a reset, a TLS handshake
timeout, an unexpected EOF, a name that did not resolve, a gateway 502/503/504) and retries after each pause of
`TRACKER_RETRY_PAUSES` (2, 8 and 30 seconds), whatever `check` says, because a transport error is never the
tracker's answer; the last attempt's result is what `check` judges, and the error then names the attempts. Any other
failure raises at once. Why: measured on one host, `api.github.com` resolved to one of six addresses at a time, one of
them refused connects for about a minute while the other five answered in milliseconds, and in one day two of five
planned cycles and three close-out writes were lost to single timeouts that a fresh dial would have survived.

## Red-batch rules

| Failure | What happens |
|---|---|
| Names members (a path only some members' diffs touch, or the project's `attribute` hook) | those members are returned to their owners with the log; the **remaining members are re-gated as a new set** |
| Names nobody | bisect: gate the first half; green lands at once and the other half is red by inference (it splits without a gate); red splits again and the other half is gated; one member left red is returned with the log |
| `::error::<stage>: INFRASTRUCTURE ...` | the same set is re-gated once; nobody is dropped, held out or bisected; a second one ends the cycle with everyone back in the queue, unfaulted |
| The gate's rebase left nothing to land (`dropped every commit as already upstream`, `emptyPattern`: the set changed only regenerated files, which the regeneration put back, or work already on the integration branch) | **terminal, never a red**: every member is marked `landed nothing (regenerate-only or already on the integration branch)`, told once, dropped at its tip (the queue reads `train-dropped` and never plans that tip again); nothing closed, nobody bisected or re-gated; the batch limit is unchanged. Inside a bisection an empty half puts the other half red by inference. Measured: a train of two such members bisected until it was killed by hand |
| Every retested file fails on the integration branch alone (the gate's `merge-to-integration: RED-BASE --` line, or its per-file retest lines `<file>: fails on origin/<integration> too (red base, not this change's)` with no file `passes on` or `not named on` the base; #7130: train 253's gate had compared its two runs' summary lines, unequal by a wall time alone, and called the base's red the member's) | **red base, nobody's**: the cycle ends with everyone in the queue unfaulted and the limit unchanged; the report names the files (`red base: <files>`); the project's `redBase` hook runs with the train, the base, the files and the kept log in its environment (`AUTOCODER_TRAIN_BRANCH`, `AUTOCODER_TRAIN_BASE`, `AUTOCODER_TRAIN_INTEGRATION`, `AUTOCODER_RED_BASE_FILES` one per line, `AUTOCODER_RED_BASE_LINE`, `AUTOCODER_RED_BASE_LOG`) to file or reuse the red-integration issue, and cannot change the verdict; the ledger's batch row is `red` with cause `red-integration`, the batch history says `red-base` |
| The regeneration fails on the assembled tree | the members whose diff touches the files its output names (or the `attribute` hook names) are named; when it names nobody, each member is tried **alone** (merged onto the base by itself under the train switch, then the hook; a member that does not merge alone is not this failure's) and the members whose own tree fails are **returned to their owners**, so the next cycle trains the rest; every member failing alone, or a failure no member reproduces, blames nobody (#364). Nothing is gated this cycle |
| Scratch fault | nobody is blamed; nothing is gated |
| Gate budget (`maxGates` after the first) spent | undecided members stay in the queue, unfaulted |

One bad member of eight: a bad member in the last half-chain costs three further gates while seven land; a bad member in the first costs more (a red gate lands nothing, so the good members behind it need green gates of their own), bounded by twice the depth. Two gates at once (one per half) is not implemented; the halves gate one after the other.

**Member accounting** is `cycle.json` plus git, never the tracker. A tracker call that fails is queued in `pending.json` and retried at the next cycle's start (`status` shows the count); it cannot change who is in a set, who landed or who was returned. A cycle left by a dead process is reconciled against git at the next start: landed members are closed out, the rest requeued, the train branch deleted.

**Adaptive size**: `batch.json` holds the limit (start `batchStart` 8, +1 after a green first gate up to `batchMax`, halved after a red one down to `batchMin`; an infrastructure red, a red base, an empty landing or an abort leaves it, recorded under its own word) and the last 50 batches.

## A flaky red is nobody's

A gate that fails on the integrated tree first re-runs the files that failed on the SAME tree (the gate
command honours `AUTOCODER_GATE_RETEST_FILES` as a list, so this is one targeted run). When they pass, the
failure did not reproduce: merge-to-integration.sh refuses with `merge-to-integration: FLAKY -- <files> ...`
(nothing lands, nobody is blamed, the gate cache forgets the tree), and the train re-gates the same set once
(`flakyRegates`, default 1) instead of bisecting it; a second flaky verdict ends the cycle with every member in
the queue and the report issue naming the files. A flake is filed and fixed, never landed over.
`AUTOCODER_GATE_FLAKY_RETEST=0` turns the retest off. Why: a one-test timeout under host load once bisected a
seven-member train for an hour and returned a member that had nothing to do with it.

## The documents fast lane lands between gate passes

The publisher's fast lane used to ride behind the whole cycle: a cycle that bisects for hours held its batch
marker and documents-only commits starved behind it (#379). The train now drains the lane after every gate
pass that did not land (a red, an infrastructure or flaky refusal, a nothing-to-land) and at the cycle's end: a
documents-only landing never re-gates anyone, so it costs the cycle nothing.

## The dependency-bot pass once per tick (`train.depbot`)

With a `train.depbot` object in the config (README.md "Merge trains": the dependency-bot pass), the tick runs
`train_depbot.Pass` at most once per `everySeconds` (default 900; the stamp `depbot.last` in the state dir), after
its own fetch, and logs the status segment (`dependency-bot pass in 3s: depbot: 2 open, oldest 1 passes (...)`): every
open PR by a configured bot author gets a tracking issue with a READY the planner accepts (the `stack:` line) first in
priority, a moved tip a new READY, a replaced PR supersedes its older issue. A pass that cannot read PRs records
`unknown`, never zero; a pass that raises is logged and the tick goes on. In step 5 a landed tracking issue closes its
PR with a comment naming the landed sha (`train_depbot.close_landed_pr`) before the member branch is deleted; a branch
kept (moved after the plan) keeps its PR open, and the next pass reports the open PR on a closed tracking issue.

## A project command once per tick (`tickCmd`)

`tickCmd` is a project command the daemon runs from its tick, at most once per `tickCmdEverySeconds`
(default 900) under `tickCmdTimeoutSeconds` (default 3600), logged in one line and never fatal to the tick: the
place for the project's own queue pass (filing a bot PR's tracking issue, starting a hotfix lane, telling a
stale tip), so nothing depends on a person running it. `AUTOCODER_TRAIN_TICK_CMD` overrides the key.

## `train` keys read here (the rest are in README.md "Merge trains")

`gate` (command template; `{train} {sha} {issue} {integration} {test_cmd}` are shell-quoted; default `merge-to-integration.sh --feature ... --issue {gateIssue} ...`), `gateIssue`, `testCmd`, `batchStart`, `batchMin`, `batchMax`, `maxGates`, `infraRegates` (1), `infraPattern`, `emptyPattern` (the gate's nothing-to-land lines, anchored to its own markers), `reportIssue` (batch-level notes; empty = member issues only), `swarm` (prefix of every tracker write), `timingsCmd` (default: `landing-timings.py` beside these scripts when present), `gateLogDir`, `hooks.preflight`, `hooks.regenerate` (run in the scratch; `AUTOCODER_TRAIN_BASE` is the base sha), `hooks.attribute` (stdin: the failure text; `AUTOCODER_TRAIN_MEMBERS`: `issue<TAB>tip` rows; prints the named issues), `hooks.landed` (run in the repo after a landing; see step 5).

A cycle launched by the daemon receives the tick's launchable list: the plan lists again (a tip may have moved during the preflight), gives an `unlisted` row to every item listed then and absent now, logs every difference between the two lists and every skip row of its plan, keeps the plan's rows and skips in `plan.json` (across cycles, beside `cycle.json`), and writes a `plan-dropped` lifecycle event per candidate it could not judge (an `unread` READY, a lost listing, an item launchable at the tick and not in the plan). One item's failed tracker read marks that item `unread` and the plan goes on; the item is read again next cycle. Timing rows (`ready` the first time the queue sees a READY, stamped with the comment's time, once per issue and comment; `launched` per member when a cycle plans it; `batched`, `landed` (naming the landed commit, by which the report looks up the integration branch's CI verdict), `returned` per member; one `batch` row per gate with the assembly seconds, and a second row with the publish seconds after a green close-out) go through `landing-timings.py`, every row naming the repository (`AUTOCODER_LANDING_REPO`, from `repo-id-fns.sh`). The gate command runs with `AUTOCODER_LANDING_BATCH` (the train's id), `AUTOCODER_LANDING_MEMBERS` (the members, comma-separated) and `AUTOCODER_LANDING_REPO` in its environment, so a `merge-to-integration.sh` inside it writes its batch row under the train's id instead of a solo row of the gate issue; `landing-report.py` merges the two rows of one id. A gate that ends by a signal with no verdict line is `infra` (re-gated once, nobody blamed), and when a killed gate left no `gate-end` in the lifecycle ledger the train writes one (`aborted`). `landing-report.py --week` is the weekly report (README-measurement-tooling.md). Exit codes: 0 cycle ran or nothing to train, 1 refused (lease, preflight), 2 planner or scratch fault, 3 environment error; `daemon`: 0 stopped, 1 another daemon holds the lock. Tests: `tests/test_merge_train_run.py`.
